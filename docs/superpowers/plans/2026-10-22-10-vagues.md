# Étape 10 : Vagues (constitution, pesée et présence par vague) — plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** l'organisateur crée des vagues (« Samedi matin », « Dimanche »…) qui regroupent des catégories par règles (tranches d'âge, disciplines) et par choix individuels ; chaque vague a sa propre pesée, sa présence et sa clôture de pesée, sans toucher aux autres vagues.

**Architecture:** la vague d'une catégorie n'est pas stockée : elle est **calculée** (`waveOfCategory`) à partir des règles des vagues et d'un éventuel choix individuel (`categories.wave_override`), ce qui place d'office les catégories créées plus tard. La présence passe du combattant à l'**inscription** (`registrations.presence`) : le moteur de recasement raisonne déjà par inscription. Sans vague définie, l'app se comporte exactement comme aujourd'hui (une vague implicite).

**Tech Stack:** TypeScript, Drizzle (SQLite, migration écrite à la main), Fastify, React 19 + Mantine 8, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-22-ordre-de-passage-et-aides-design.md` §1.3 (vagues) et §1.4 (pesée par vague). Hors de cette étape : recasement par vague (étape 11), lancement / figeage (étapes 12-13).

## Global Constraints
- Vague : `id`, `name` (non vide, ≤ 40 caractères, unique sans tenir compte de la casse ni des accents), `order`, `rules` = `{ ageBandCodes: string[]; disciplines: DisciplineId[] }`, `weighInClosed`. Au plus 20 vagues ; zéro vague = comportement actuel.
- **Règle** : une catégorie correspond à une vague si (aucune tranche dans la règle **ou** sa plus jeune tranche y figure) **et** (aucune discipline **ou** sa discipline y figure), avec au moins une tranche ou une discipline dans la règle (une règle vide ne prend rien d'office).
- **Vague d'une catégorie** = son choix individuel s'il existe (`wave_override` = id d'une vague, ou `'none'` = en attente) ; sinon la **première** vague (dans l'ordre) dont la règle correspond ; sinon aucune (« en attente »). Une catégorie qui correspond aux règles de plusieurs vagues est **signalée** (elle va dans la première).
- Une vague supprimée : les choix individuels qui la visaient sont effacés (les catégories retombent sur les règles).
- **Présence par inscription** : pointer un combattant dans une vague règle la présence de **ses inscriptions dont la catégorie est dans cette vague** ; le poids reste celui du combattant. Taper un poids marque présent dans la vague pesée.
- **Clôture de la pesée d'une vague** : marque absentes les inscriptions encore « non pesées » **de cette vague seulement**, et marque la vague « pesée clôturée ».
- Sans vague : liste, présence et clôture portent sur toutes les inscriptions, comme aujourd'hui (`competitions.weigh_in_closed`).
- Migration : la présence actuelle de chaque combattant est recopiée sur chacune de ses inscriptions ; aucune autre donnée ne change.
- Vocabulaire : « vague », « en attente » ; aides (`src/web/help.ts`) pour les nouveaux écrans.
- Tous les tests restent verts : `npm run typecheck && npm test && npm run test:e2e`.

## Review Focus
- **Base existante** : présences et pesée clôturée conservées après migration (un absent reste absent) — test Task 2.
- **Combattant dans deux vagues** (kata le matin, combat l'après-midi) : présent le matin, absent l'après-midi, sans que l'un écrase l'autre — test Task 3.
- **Clôturer la pesée du matin** ne marque jamais absent un combattant de l'après-midi — test Task 3.
- **Catégorie créée après coup** (inscription sur place) : rejoint la vague de sa tranche d'office — test Task 2.
- **Sans vague** : tous les parcours existants (pesée, recasement, jour J) inchangés — suite e2e complète.
