# Étape 3 : Import FFK et rapprochement — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** importer l'export FFK (.xlsx, .ods ou .csv) quel que soit l'ordre des onglets et des colonnes, le **rapprocher des fiches club** (par nom + club, sans licence), montrer un aperçu des différences, puis appliquer : ajouts, mises à jour (l'export FFK fait foi), retraits, catégories manquantes créées. Le réimport ne crée pas de doublons.

**Architecture :**
- Toute la logique de lecture et de rapprochement est **pure**, dans `src/domain/ffk-import.ts` :
  - `guessColumnMapping` ;
  - `parseFfkRows` ;
  - `planFfkImport`, qui produit un **plan** (ce qui sera créé, modifié, retiré, et ce qui reste douteux).
- Le serveur garde le fichier envoyé (table `uploads`), recalcule le plan à chaque changement de choix de l'organisateur (correspondance des colonnes, liens de clubs, décisions sur les cas douteux), puis l'applique dans une transaction.
- Les correspondances de colonnes et les liens club ↔ entité FFK sont **mémorisés** d'une compétition à l'autre.

**Tech Stack :** celle des étapes 1 et 2 (SheetJS pour lire les fichiers).

**Spec :** §6 (import FFK), §7.3 (rapprochement), §4.3 (catégorie inconnue créée automatiquement, « Veteran » sans numéro → V1). Feuille de route : `docs/superpowers/plans/2026-10-21-00-feuille-de-route.md`.

## Global Constraints

- Toutes les contraintes des étapes 1 et 2 s'appliquent : français, hors ligne, Chrome, domaine pur, dépôt `async`, identifiants stables des catégories.
- **L'export FFK fait foi** (spec §7.1) pour l'âge, le poids, la discipline et le club. **Exception** : son règlement est presque toujours vide. Un règlement vide côté FFK **ne remplace jamais** celui de la fiche club. Pour une nouvelle inscription sans règlement, on prend **jiyu**, avec une remarque.
- La colonne FFK `Type` contient la **discipline** ; la colonne `Discipline` contient le **règlement** (spec §6.1).
- **Rien n'est appliqué sans aperçu** : `preview`, puis `commit`, avec les mêmes choix.
- Rapprochement **sûr** = automatique ; **douteux** = proposé, à confirmer (spec §7.3).
- **Données personnelles** : `coupe-shidokan.xlsx` n'est **jamais** commité ni copié dans les tests. Les tests utilisent un fichier **construit** avec la même structure et des noms fictifs.

## Review Focus

1. **Réimport d'un export FFK mis à jour** (un ajout, un retrait, un changement de poids) : pas de doublon ; le retrait ne touche que les inscriptions d'origine FFK des disciplines importées ; une inscription venant d'une fiche club devient « sans FFK » au lieu d'être supprimée. Test en Task 2.
2. **Le vrai fichier `coupe-shidokan.xlsx`** : il s'importe sans plantage, avec des comptes cohérents (152 inscriptions, 1 licence sur deux onglets, 1 ligne sans licence ni âge signalée). Vérification par script local non commité en Task 3.
3. **Homonymes et noms inversés** (« DUPONT LYNA » contre « Lyna Dupont », deux « MARTIN » dans le même club) : jamais rapprochés en silence s'ils sont ambigus. Test en Task 2.
4. **Catégorie inconnue** (Poussins -20) : créée dans la grille avec une remarque. Une catégorie **ouverte** inconnue (« +80 » alors que la grille a « +84 ») est signalée en erreur sur la ligne, sans casser la grille. Tests en Tasks 1 et 3.
5. **Signes moins Unicode** (« −35 », « –35 »), copiés depuis Word ou Excel : lus comme « -35 ». Test en Task 1 (mineur reporté de l'étape 1).

### Task 2 : Domaine — plan d'import et rapprochement

**Files :**
- Modify : `src/domain/ffk-import.ts` (deuxième partie)
- Test : `tests/domain/ffk-import.test.ts` (ajouts)

**Interfaces :**
- Consumes : Task 1 ; `Club`, `Fighter`, `Registration` (étape 2) ; `CategoryGrid` ; `weightClassesFor`.
- Produces :

```ts
export interface ExistingData { clubs: Club[]; fighters: Fighter[]; registrations: (Registration & { ffkConfirmed: boolean })[]; aliases: Record<string, string> } // aliases : nameKey de club de fiche → clubEntity FFK
export type ClubLink = { clubEntity: string; clubName: string; target: { kind: 'existing'; clubId: string } | { kind: 'new' }; certainty: 'sure' | 'doubtful' | 'new'; candidates: { clubId: string; name: string }[] };
export type FighterDecision = string | 'new'; // id de combattant existant, ou nouveau
export interface FfkChoices { clubLinks?: Record<string, string | 'new'>; decisions?: Record<string, FighterDecision> } // clés : clubEntity / FfkRow.key
export type PlanItem =
  | { kind: 'create'; row: FfkRow; fighterId: string | 'new'; weightClassId: string | null }
  | { kind: 'update'; row: FfkRow; registrationId: string; fighterId: string; weightClassId: string | null; changes: string[] } // changes : libellés FR (« Poids : -54 → -61 »)
  | { kind: 'doubtful'; row: FfkRow; candidates: { fighterId: string; label: string; reason: string }[] }
  | { kind: 'error'; row: FfkRow };
export interface FfkImportPlan {
  clubs: ClubLink[];
  items: PlanItem[];
  newWeightClasses: WeightClass[];            // catégories inconnues à créer (non ouvertes)
  removals: { registrationId: string; label: string }[];          // origine FFK, absentes de l'import, disciplines importées seulement
  unconfirmed: { registrationId: string; label: string }[];        // fiches club sans inscription FFK (dont celles qui perdent la confirmation)
  summary: { create: number; update: number; doubtful: number; errors: number; removals: number; newWeightClasses: number };
}
export function planFfkImport(rows: FfkRow[], grid: CategoryGrid, existing: ExistingData, choices?: FfkChoices): FfkImportPlan;
```

  Règles (spec §7.3) :
  - **Club** : choix explicite d'abord ; sinon un club existant avec le même `ffkEntity` ; sinon un alias mémorisé ; sinon un club dont le nom normalisé est **égal** au nom FFK sans code (sûr) ; sinon **contenu** dans l'autre, dans un sens ou l'autre (douteux, proposé) ; sinon nouveau club.
  - **Combattant**, dans le club lié, même sexe :
    - **sûr** si même licence, ou même nom complet normalisé, dans l'ordre « NOM PRÉNOM » ou « PRÉNOM NOM ». S'il y a **plusieurs** candidats sûrs, la ligne est douteuse ;
    - **douteux** si même nom de famille avec un prénom différent, ou une distance d'édition ≤ 2 sur le nom complet normalisé, ou un nom identique dans **un autre club**.
  - La décision explicite (`choices.decisions[row.key]`) l'emporte.
  - **Inscription** : pour le combattant trouvé, l'inscription de même discipline est **mise à jour** ; sinon elle est **créée**. Les `changes` listent âge, poids, club et règlement (seulement si le règlement FFK n'est pas vide).
  - **Retraits** : les inscriptions `source = 'ffk'` absentes de l'import, **seulement pour les disciplines présentes** dans l'import.
  - **Non confirmées** : les inscriptions `club_form`, `manual` ou `onsite` qu'aucune ligne n'a rapprochées.
  - Deux lignes FFK pour la même licence et la même discipline → la seconde est une erreur « en double ».

  `applyFfkPlan` refuse un plan qui contient encore des `doubtful` (`RegistrationValidationError('Des rapprochements douteux restent à trancher.')`). Sinon, en une transaction :
  1. ajoute `newWeightClasses` à la grille (les catégories gardent leur ordre par poids) ;
  2. crée ou relie les clubs (`ffkEntity` renseigné) et mémorise les alias `nameKey(club de fiche) → clubEntity` ;
  3. crée ou met à jour les combattants (la licence est renseignée ; l'âge et le sexe suivent l'export FFK). Les lignes `'new'` d'une même licence partagent un seul combattant ;
  4. crée les inscriptions (`source: 'ffk'`, `ffkConfirmed: true`, règlement jiyu par défaut) ou les met à jour (`ffkConfirmed: true`) ;
  5. supprime les `removals`, et passe `ffkConfirmed = false` sur les inscriptions non confirmées ;
  6. mémorise les correspondances de colonnes.

  - Routes (préfixe `/api/competitions/:id`) :

| Méthode | Route | Corps | Réponse |
|---|---|---|---|
| POST | `/ffk-imports` | fichier brut (+ en-tête `X-File-Name`) | `{ uploadId, sheets: { name, headerRow, headers: string[], mapping: ColumnMapping, include: boolean }[] }` (mapping mémorisé sinon deviné ; `include` vrai si ≥ 3 champs reconnus) |
| POST | `/ffk-imports/:uploadId/preview` | `{ sheets: { name, headerRow, mapping, include }[], choices?: FfkChoices }` | `FfkImportPlan` |
| POST | `/ffk-imports/:uploadId/commit` | même corps | `{ created, updated, removed, weightClassesCreated }` |
